# Milestone 1: Daily driver

Goal: a player the owner can switch daily listening to, including Android Auto, with the security
foundations in place from the first commit.

Gate: the owner uses it as the only podcast player for a week and nothing is lost (positions, downloads,
subscriptions), with no crash.

Out of scope for M1: ad skipping, chapters UI, skip intro/outro, loudness normalization, Inbox, sync,
server, translation, widget, Wear OS. Put requests for these under "Later" in `docs/PROGRESS.md`.

## How to run a session

Paste this into Claude Code, changing the session id (or use `/session M1-S1` if the command file is present):

> Read CLAUDE.md, docs/PROGRESS.md, and session M1-S1 in docs/milestones/M1.md.
> Plan that session only: list the files you will create or change, the tests you will write first,
> and anything in the spec that seems unclear. Wait for my approval before writing code.

Start each session in plan mode. After approving the plan, let it build. At the end it must pass
`./gradlew check`, update `docs/PROGRESS.md` and open a pull request; with `/session` it then waits for CI,
installs the debug build on the connected phone, says what to check, and merges when the owner says yes.

If a session gets long, ask it to update `docs/PROGRESS.md` and commit, then run `/clear` and say:
"Continue M1-S<n> from docs/PROGRESS.md."

## Running several sessions in a row

Sessions whose results are proven by tests can run back to back without the owner approving each plan.
Start Claude Code with `claude --permission-mode acceptEdits` and type, for example, `/batch M1-S2 M1-S3 M1-S4`.
The batch command runs each session in a fresh subagent, merges it when CI is green, and stops at the first
problem. Recommended grouping:

| Run | How | Owner checks afterwards |
| --- | --- | --- |
| M1-S1 | `/session`, attended | Dark shell on the phone; CI green |
| M1-S2, S3, S4 | `/batch` | Skim the three pull requests and `docs/PROGRESS.md` |
| M1-S5, S6 | `/batch` | Developer screen: add a feed, refresh, download, artwork appears |
| M1-S7 | `/session`, attended | Developer screen playback, lock screen, kill and resume, Bluetooth |
| M1-S8, S9 | `/batch` | Use the app for a day |
| M1-S9a, S9b | `/batch` | Star a few episodes; import a list; turn on auto-download for a show |
| M1-S9c | `/session`, attended | Podbean shows and favorites arrive; review what didn't match |
| M1-S10 | `/session`, attended | Desktop Head Unit, then the car |
| M1-S11 | `/session`, attended | Acceptance checklist, then the milestone review |

## M1-S2 Network gate

Read first: SPEC §3; LESSONS rows "Downloads".

Build in `:core:net`
- The single OkHttp client factory: timeouts, user agent, no automatic redirects, connection pool.
- Address-filtering `Dns` (and literal-IP check) with the owner-approved-host exception.
- Manual redirect handling: max 5 hops, each re-checked, reporting whether the final hop was permanent.
- URL policy: allowed schemes; `redact(url)`.
- Size-limited body reading for feeds, OPML, chapters and images (SPEC §3 limits).
- Conditional GET helper storing ETag and Last-Modified.
- Range download engine (pure Kotlin): resume with `Range` + `If-Range`, detect servers that ignore Range,
  stall timeout, progress callbacks, clean cancellation. No Android imports.

Tests (MockWebServer): redirect to 127.0.0.1, 10.x, 169.254.169.254, [::1] and fc00:: is refused; redirect loop
stops at 5; typed local host is allowed only for that host; 301 vs 302 reporting; body over the limit is
refused; Range resume; server ignoring Range; slow drip triggers the stall timeout; `redact` strips query,
fragment and userinfo.

Done when: all of the above pass and nothing in the module imports `android.*`.

## M1-S9b Auto-download and clean-up

Read first: SPEC §9 (Auto-download, Clean-up), §12 (Settings); LESSONS rows "Downloads", "Storage".

Build in `:core:jobs`, `:core:data` and `:app`
- Per-show "Download new episodes" (show page) and a global default for new subscriptions (off); only episodes
  published after it was turned on; enqueued after each refresh as background work.
- Auto-download network setting: any connection (default) or Wi-Fi only, separate from manual downloads.
- Storage cap respected: at the cap auto-downloads stop with a plain message; nothing is deleted to make room.
- Clean-up: played (98%) deleted after 3 days, unplayed downloads after 14 days, both configurable; never
  starred, queued or loaded episodes; optional "keep starred episodes downloaded"; daily and after an episode
  is marked played; every deletion in the download log.
- Settings › Downloads and storage gains these settings.

Tests: only new episodes are auto-downloaded; the network setting maps to the right constraint; the cap stops
auto-downloads without deleting; each clean-up rule and each exemption; clean-up and a running download of the
same episode don't race; settings persist and travel in backups.

Done when: a show with auto-download on gets its new episodes without the owner asking, and old ones disappear
on schedule.
